# Задание для Codex: визуальная матрица задач поверх Singularity

Разработай и доведи до рабочего состояния первую версию личного приложения для визуального планирования, интегрированного с SingularityApp. Нужны работающий код, запуск, проверки и инструкция. Не останавливайся на плане или макете.

## 1. Контекст и цель

Я использую Singularity как планировщик. Мне нужна свободная доска наподобие Holst: внутри четырёх квадрантов размещаются задачи, снаружи — проекты; задача может быть связана с несколькими проектами. Размер карточки помогает визуально обозначать её важность.

Хочу создавать задачу один раз и работать с ней через два интерфейса: Singularity и нашу доску. Задачи, введённые с телефона в Singularity, должны появляться на доске автоматически после синхронизации.

Это собственное приложение поверх официального API Singularity. Интеграция с Holst и порт отладки не нужны. Для обычной работы приложения не нужен ИИ или постоянно запущенный Codex.

## 2. Как выполнять работу

- Сначала прочитай AGENTS.md, изучи текущий репозиторий и доступное окружение. Сохрани существующие изменения пользователя.
- Если проект уже начат, используй его архитектуру. Для нового проекта возьми простой монолит: Java 21, Spring Boot, Maven Wrapper, PostgreSQL и Liquibase; интерфейс — React, TypeScript, Vite и React Flow. Зафиксируй совместимые версии зависимостей. Моя основная специализация — Java, поэтому код должен быть удобен для дальнейшей поддержки.
- Кратко опиши принятые решения и сразу переходи к реализации. Обычные технические решения принимай самостоятельно.
- Неизвестные подписи осей и квадрантов сделай настраиваемыми. Их отсутствие не должно блокировать разработку.
- Если нет токена, реализуй и проверь всё на демонстрационном адаптере, сохранив полноценный адаптер реального API. Отдельно сообщи, что реально проверено, а что требует подключения аккаунта.
- Если внешний сервис или окружение блокирует часть проверки, продолжай независимую работу и точно опиши ограничение. Не выдавай заглушку за завершённую интеграцию.
- Не публикуй приложение в интернете. Первая версия предназначена для одного пользователя и локального запуска на Fedora.

## 3. Модель данных и источник истины

Используй следующую модель:

| Объект или свойство | Основное место хранения |
| --- | --- |
| Задача: название, описание, даты, выполнение, обычные теги | Singularity |
| Проект нашей доски: название и идентификатор | Тег Singularity |
| Связь задачи с проектом доски | Наличие соответствующего тега у задачи |
| Координаты и размеры карточек, положение проектов, настройки матрицы | Наша база данных |
| Дополнительное описание и состояние проекта доски, если понадобятся | Наша база данных |

Правила:

- Проекты доски сопоставляются тегам Singularity. Это даёт связь многие ко многим без копирования задач.
- Для проектных тегов используется выбранная ветка «Проекты доски». Её корневой ID хранится в настройках; сам корень проектом не считается. Обрабатывай потомков выбранного корня, обычные теги вне этой ветки остаются обычными тегами.
- Предусмотри выбор существующего корневого тега и явное действие пользователя для создания нового. Не создавай теги при простом запуске или чтении данных.
- У проекта доски есть singularityTagId, у карточки — singularityTaskId. Сопоставление выполняется по ID, а не по названиям.
- Источником связей служат теги задачи. Локальная копия связей допустима как кэш; не создавай второй независимо редактируемый источник истины.
- Родные проекты Singularity сохраняют своё назначение. Не переноси задачи между ними из-за изменения связей на доске.
- Переименование тега обновляет название проекта и сохраняет его положение и связи.
- У одной задачи на доске одна карточка, даже если у неё несколько проектов.
- Линия «задача — проект» означает принадлежность, а не зависимость выполнения.
- Удалённый во внешней системе тег не должен автоматически создаваться заново. Сохрани локальную раскладку для возможного восстановления и покажи понятное состояние.

## 4. Интерфейс первой версии

Весь интерфейс — на русском языке.

### Доска

- Свободное масштабирование и перемещение по полотну.
- Четыре визуально различимых квадранта с редактируемыми названиями и подписями осей. До настройки используй нейтральные подписи.
- Не зашивай смысл «срочно / важно»: это пользовательская матрица.
- За пределами матрицы — свободно перемещаемые карточки проектов.
- Область «Неразобранное» для новых задач без сохранённого положения.
- Перетаскивание и изменение размеров карточек задач. Размер пока является визуальным свойством: не меняй из-за него приоритет в Singularity.
- Положение внутри матрицы пока хранится локально: не меняй сроки или другие поля задачи по координатам.
- Автосохранение раскладки с небольшой задержкой после действий.
- Обновление данных не должно менять вручную заданные координаты, размеры, масштаб и положение просмотра.
- Поиск задач, фильтр по проекту, переключатель показа выполненных.
- При выборе проекта подсвечивай его задачи и связи; остальные можно приглушить.
- Покажи состояние соединения и синхронизации, время последнего успешного обновления, ошибки и кнопку повторной попытки.

### Задачи и проекты

- Быстрое создание задачи через поле ввода и Enter; создание двойным щелчком на свободном месте доски.
- Боковая панель редактирования: название, описание, дата выполнения/начала и крайний срок как отдельные поля, проектные теги, выполнение.
- Создание проекта доски создаёт тег внутри выбранной ветки. Позволь добавить на доску уже существующий проектный тег.
- Создание линии к проекту добавляет соответствующий тег к задаче.
- Удаление линии снимает только этот тег и не удаляет задачу.
- Завершение задачи обновляет её в Singularity; внешнее завершение отражается на доске.
- Скрытие карточки с доски не удаляет задачу из Singularity. Скрытую карточку можно вернуть через список.
- Не добавляй безвозвратное удаление реальных задач в первую версию.
- Область синхронизации должна быть явной: активные задачи личного аккаунта по умолчанию, с возможностью ограничить её родными проектами Singularity. Применение фильтра не удаляет раскладку.
- Основной интерфейс рассчитан на ноутбук; панель свойств и быстрый ввод должны оставаться пригодными при узком окне.

## 5. Реальный API Singularity

Перед реализацией клиента изучи актуальную официальную документацию:

- https://singularity-app.ru/wiki/api/
- https://api.singularity-app.com/v2/api
- https://api.singularity-app.com/v2/api-json

Используй REST API v2. Не придумывай адреса методов, поля, правила авторизации и ограничения. Проверяй конкретные схемы запросов и ответов, особенно чтение задач и тегов, присвоение тегов, завершение и повторяющиеся задачи.

В ранее проверенной спецификации TaskUpdateDto содержит поле tags — массив ID тегов, а обновление задачи выполняется через PATCH /v2/task/{id}. Повторно проверь это перед реализацией и выясни, заменяет ли tags весь набор.

Дополнительные требования:

- Все запросы к Singularity выполняет сервер приложения.
- Токен берётся из локальной переменной окружения SINGULARITY_API_TOKEN. Не помещай его в браузер, localStorage, исходники или логи. Подготовь .env.example и исключи .env из Git.
- Для демонстрационного запуска токен не нужен. Режимы demo и real должны быть явно различимы; ошибка реального API не должна незаметно включать демонстрационные данные.
- Обрабатывай пагинацию. Изучи особенности выдачи повторяющихся задач и includeAllRecurrenceInstances, чтобы не терять записи.
- Дату без времени не превращай в другой календарный день при преобразовании часового пояса. Часовой пояс по умолчанию — Europe/Moscow, с возможностью настройки.
- Проверь формат описания задачи. Если это Quill Delta или другой структурированный формат, не записывай вместо него произвольную строку и не уничтожай форматирование при изменении других полей.
- Для первой версии достаточно создавать обычные задачи. Существующие повторяющиеся задачи обрабатывай только в пределах подтверждённой семантики API; неподдерживаемые действия явно отключи, не меняя правило повторения.
- Приложение должно обращаться только к предусмотренному официальному API; автоматизация браузера для интеграции не нужна.

## 6. Синхронизация и сохранность данных

- При подключении выполняй первоначальную загрузку, затем периодическое обновление и обновление по кнопке. Используй modifiedSince только после проверки его семантики; предусмотри сверку полного состояния.
- Интервал обновления настраивается. Не допускай параллельных циклов, бесконечных запросов и потери пагинации.
- Изменения с нашей доски отправляй сразу; внешний интерфейс обновляется после синхронизации. Не обещай мгновенную доставку внешних изменений.
- Меняй только поля, которые действительно редактировал пользователь.
- При добавлении или снятии проектного тега сохраняй все остальные теги задачи. Работай с намерением «добавить / снять конкретный ID», а не со старым локальным снимком полного массива.
- Сериализуй исходящие изменения одной задачи. Повторное чтение перед записью снижает риск конфликта, но без условной записи API не гарантирует атомарность. Не заявляй защиты от всех гонок, если сервер её не предоставляет.
- При обнаруженном конфликте покажи различия и предложи выбрать результат; не перезаписывай внешние изменения молча.
- Сохраняй ожидающие операции и их состояние в БД. Пользователь должен видеть, что ещё не сохранено, что отправлено и что завершилось ошибкой.
- После неоднозначного тайм-аута создания не повторяй POST вслепую: сначала проверь результат операции. Изучи externalId и доступные средства идемпотентности. Не предполагай уникальность externalId без подтверждения.
- Обрабатывай недоступность сети, 401/403, ограничения частоты и 5xx. Используй ограниченные повторы с увеличением задержки там, где они безопасны.
- Повторная загрузка не создаёт дубликатов задач, тегов или карточек.
- Сбой API не стирает раскладку. Данные доски сохраняются после перезапуска приложения и контейнеров.

## 7. Объём и устройство реализации

Одна доска и один пользователь достаточны для первой версии.

Раздели код на интерфейс доски, прикладную логику, хранение, синхронизацию и адаптер Singularity. Не вводи микросервисы, Kafka, универсальную платформу интеграций или собственный механизм напоминаний.

Нужны два адаптера с одинаковым контрактом:

1. Реальный клиент Singularity.
2. Демонстрационный адаптер с изменяемыми и сохраняемыми данными.

Подготовь 12–15 демонстрационных задач и 3–4 проекта, включая задачу с двумя проектами и несколькими обычными тегами. Демонстрационный режим не должен отправлять запросы в мой аккаунт.

Сделай воспроизводимый запуск через Docker Compose, постоянный том БД, миграции, проверку готовности сервисов и краткие команды разработки. Публикуй порты только на 127.0.0.1. Продумай резервное копирование локальной раскладки и настроек; она не восстанавливается из одних тегов Singularity.

## 8. Проверки и критерии готовности

Добавь осмысленные проверки поведения, используя поддельный HTTP-сервер для API и браузерные проверки основных сценариев. Не обращайся к реальному аккаунту в автоматических тестах.

Проверь:

- одна задача связана с двумя проектами без дублирования;
- добавление и снятие проектного тега сохраняет обычные теги;
- переименование тега не разрушает соответствие по ID;
- новые внешние задачи попадают в «Неразобранное»;
- внешнее изменение тегов и выполнения обновляет доску;
- синхронизация и перезапуск сохраняют координаты и размеры;
- скрытие карточки не удаляет задачу;
- пагинация не пропускает записи;
- повторная отправка и неоднозначный тайм-аут не вызывают слепого повторного создания;
- ошибки и конфликты видимы пользователю, несохранённые изменения не теряются;
- даты и описания проходят преобразование без незаметной порчи данных.

Первая версия готова, когда её можно запустить по README без токена, пройти демонстрационные сценарии, а затем подключить реальный аккаунт через документированные настройки без переписывания кода.

В конце сообщи:
- что реализовано;
- как запустить и подключить Singularity;
- какие команды проверок выполнены и их результат;
- что проверено только на демонстрационных данных;
- какие ограничения остались.

Начни с изучения репозитория и спецификации API, затем последовательно реализуй, запусти и проверь приложение.
