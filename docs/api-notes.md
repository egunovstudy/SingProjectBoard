## Подтверждено схемой

Авторизация — `Authorization: Bearer …`. Базовый адрес `https://api.singularity-app.com`. Используются `/v2/task`, `/v2/task/{id}`, `/v2/tag`, `/v2/tag/{id}`, `/v2/project` и документированные действия задач.

Списки возвращают `tasks`, `tags` или `projects` и блок `pagination` с `total`, `count`, `offset`. Клиент задаёт `paginationData=true`, размер страницы 100 и продолжает по фактическому числу записей. Для задач всегда передаёт `includeAllRecurrenceInstances=true`: спецификация предупреждает о пропусках offset-пагинации без этого флага. Неполная или повторная страница приводит к видимой ошибке без замены кэша.

`PATCH /v2/task/{id}` поддерживает массив ID `tags`. У заметки `note` — JSON-строка массива операций Quill Delta, без оболочки `ops`. Неизменённое поле описания не отправляется. Обычные задачи завершаются через `POST /v2/task/{id}/complete` и возобновляются через `/uncomplete`.

`TaskCreateDto` также принимает `tags`. При создании задачи для выбранной цели или опасения ID тега сценария передаётся сразу в `POST /v2/task`. Очередь сверяет наличие запрошенного тега в ответе создания и при сверке по `externalId`.

`DELETE /v2/task/{id}` удаляет задачу безвозвратно и возвращает `204` без тела. Перед отправкой Орбита читает задачу по ID. При повторе после сбоя `404` или флаг `removed` означают, что задача больше недоступна. Запрос адресуется выбранной задаче. Изменения её подзадач видны после очередной синхронизации. [Руководство REST API](https://singularity-app.ru/wiki/api/) · [OpenAPI](https://api.singularity-app.com/v2/api-json)

## Консервативные решения реализации

Схема массива тегов не является гарантией атомарного добавления/снятия. Адаптер трактует его как итоговый набор: свежее чтение → изменение одного ID → PATCH → сверка результата. Условная запись и отсутствие гонок не заявляются. Семантика проверена на поддельном транспорте; реальный аккаунт из этой среды недоступен.

Даты без времени остаются строками календарного дня; строки с временем сохраняют смещение. При явном изменении начала `useTime` соответствует наличию времени. Снятие существующей даты в real отключено в текущей реализации. Поля и выполнение повторяющихся задач редактируются в Singularity. Зашифрованные задачи доступны для чтения.

`externalId` используется для сверки создания, его уникальность не предполагается. Ноль или несколько совпадений оставляют операцию неопределённой. Для создания тегов схема не предоставляет подтверждённого ключа идемпотентности; результат проверяется вручную. Возможный batch UUID не используется без подтверждения срока хранения и гарантий повторного исполнения.

`modifiedSince` не нужен для первой версии: каждый цикл выполняет полную сверку. Архив, корзина и заметки исключаются из обычной доски; завершённые доступные задачи сохраняются в кэше для переключателя. Транспорт не следует редиректам и не выводит тела ошибок API, заголовки авторизации или токен.


## Представление повторов на доске (13 ноября 2026)

Клиент продолжает читать все страницы и все экземпляры. Только представление доски объединяет записи по `recurrenceGeneratorId` (идентификатор генератора в официальной схеме) и сам генератор по его ID. Сравнение названий для объединения не используется. Для карточки выбирается самый ранний незавершённый экземпляр; при отсутствии открытых — доступный завершённый. Раскладка хранится по ID серии, при первом обновлении используются существующие координаты отдельного экземпляра. Исходный кэш и старые записи раскладки не удаляются.

Связи серии меняются через `PATCH /v2/task/{id}` по ID шаблона. В запросе передаётся только `tags` из свежего чтения с добавленным или снятым тегом сценария. На доске этот набор применяется ко всей карточке серии. Публичная схема описывает поле `tags` и ID генератора. Справка Singularity описывает, как её приложение применяет изменения шаблона к экземплярам. ## Вложенные теги и порядок шагов (20 ноября 2026)

- У тега один `parent`. `PATCH /v2/tag/{id}` принимает родителя. Поскольку актуальный `TagUpdateDto` требует `title`, Орбита отправляет текущее имя из свежего чтения. После записи она сверяет родителя. Теги задач, цвет и порядок тега не передаются.
- `TaskCreateDto` и `TaskUpdateDto` поддерживают `parent` и числовой `parentOrder`. Для проверки места шага сервер читает страницы прямых подзадач через `GET /v2/task?parent=…`. При вставке выбирает позицию между соседями. При совпадении позиций сервер разводит числовые значения, сохраняя порядок шагов, затем вставляет шаг. После записи считывает его родителя и позицию.
- Для уже существующего шага изменение отправляет только `parentOrder` и, при добавлении в цепочку, `parent`. Вынос шага из цепочки делается в Singularity. Способ очистки `parent` в PATCH схемой не оговорён.
- Связи Ганта в публичном REST v2 не описаны. Для сквозной проверки с реальным аккаунтом требуется подтвердить, что порядок, полученный из мобильного интерфейса, совпадает с сортировкой по `parentOrder`, и что клиент отражает обратную перестановку через API. Автоматические проверки используют демоданные и поддельный транспорт.
